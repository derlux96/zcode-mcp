# Design-Spec: v1.1 — Per-Call-Modellwahl (Dual-Mode-Runner)

**Datum:** 2026-10-17
**Status:** Von Nutzer freigegeben („leg los" auf den v1.1-Plan mit Dual-Mode)
**Basis:** v1-Spec `2026-10-16-grok-zcode-plugin-design.md` (unverändert gültig); Protokoll-Evidenz: `.superpowers/v1.1/protocol-notes.md`

## 1. Motivation

v1 nutzt ausschließlich den offiziellen `-p`-Headless-Pfad — der kein Per-Call-Modell kennt (kein `--model`-Flag, keine `ZCODE_MODEL`-Env, keine Slash-Interpretation; alles verifiziert 2026-10-17). Fällt der CLI-Default (Provider-Config `providerOrder[0].modelOrder[0]`) aus, schlägt JEDE delegierte Task fehl — Nutzer dürften ihre Config nicht anpassen müssen (Nutzer-Anforderung: „der MCP muss funktionieren, nicht die Leute ihre Config löschen lassen").

## 2. Design

**Dual-Mode-Runner** in `zcode_run`:

- **Modus A (Default, unverändert):** `zcode -p … --json` über den offiziellen Pfad. Kein `model`-Parameter gesetzt → exakt v1-Verhalten.
- **Modus B (neu, `model`-Parameter gesetzt):** Server spawn `zcode app-server --stdio` als Kindprozess und spricht das interne Protokoll: `session/create` (mit `workspace`) → `session/send` (mit `modelSelection` + `options.reasoningLevel`, Pflichtfeld) → Events bis `turn.completed`/`turn.failed` → Antworttext aus `payload.response`, Session-ID zurück (resumable). Beantwortet Server-Anfragen (`session/requestRuntimePreferences`) automatisch (15-s-Timeout-Falle).

**Parameter an `zcode_run`:**
- `model` (string, optional): either `"modelId"` (wird über den Katalog der create-Response einem Provider zugeordnet) oder `"providerId/modelId"`. Setzen → Modus B.
- `reasoning_level` (enum `low|medium|high|max`, Default `high`): nur Modus B (Protokoll verlangt den Wert beim Send).
- Alle v1-Parameter unverändert (`isolate_worktree` auch in Modus B: Task-cwd = Worktree-Dir).

**Fail-Isolation:** Gesamter Protokoll-Code in `src/appserver.mjs`. Protokoll-Drift (zukünftige CLI-Versionen) bricht NUR Modus B mit klarer Fehlermeldung; Modus A bleibt unberührt. Der Standardnutzer (zai-Plan, GLM-5.3) merkt nichts von Modus B.

**`zcode_check`:** neuer optionaler Parameter `include_models` (Default `false`): hängt bei `true` die verfügbaren Provider/Modelle aus dem create-Katalog an (best-effort, eigener Timeout). Ohne den Parameter bleibt der Check so schnell wie in v1.

## 3. Nicht-Ziele
- Kein Schreiben in Nutzer-Configs (provider_config.json/config.json bleiben unberührt — auch nicht tempär beim Betrieb).
- Kein volles App-Server-Facettenreichtum (Subagent-Steuerung, Settings-Mutation, v4/command) — nur die 5 benötigten Interaktionen (create/send/event/messages/resume-fähige Session-ID).
- Kein `zcode_parallel`, keine Remote-Bridge (weiter v2+).

## 4. Testing
- Unit: `test/fake-appserver.cjs` als deterministisches Protocol-Stuntdouble (inkl. Server-Request-Falle + Timeout-Pfad + turn.failed).
- E2E `--e2e` erweitert: Modus-B-Lauf mit Modell aus dem Live-Katalog (liest `settings.model.available` und wählt das erste — funktioniert auf JEDEM Provider-Setup ohne Config-Änderung; auf der Referenzmaschine der Beweis gegen Opencode GO).
- E2E Modus A bleibt wie v1 (auf Maschinen mit kaputtem Default bekannt rot — dokumentiert).
